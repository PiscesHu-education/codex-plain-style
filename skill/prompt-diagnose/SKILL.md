# 系统提示词诊断与改写

把这个 skill 当作"给模型换一副眼镜"的流程：用户的抱怨是症状，提示词是成因，改写是处方，验证是复诊。

---

## 零、先立一条认知：提示词能改什么，不能改什么

不改这条认知，后面的所有工作都会跑偏。

**提示词能改的**：模型给什么、先给什么、怎么分块、加不加粗、画不画表、在哪里停、遇到不确定时说什么、拿不准时是问你还是自己猜。
**提示词改不了的**：句子本身的通顺度、思考的深浅、真正的写作能力。这些来自模型权重，换多少字都没用。

由此推出三条操作约定：

1. 用户说"模型写得不好"时，先别急着写"请用简洁、平实的语言"。先判断他到底是嫌句子难看，还是嫌**看不见重点**。后者才是提示词该管的事。
2. 改写目标不是"让句子更顺"，是"让模型摆对重点、该结构化时结构化、该收时收"。评价提示词改动的好坏也按这个标准，不按句子通不通顺。
3. 如果用户抱怨的确实属于"改不了"那一层，直说。可以说"这是模型本身的语言能力，提示词只能改变它挑什么内容、按什么顺序给你，改不了它用不用好句子"。不应假装能改、写完就说已经解决了。

一条被反复验证的经验：**在语言风格方面对模型的限制越少，模型越可能体现出比较好的写作能力。** 不要一遇到"写得不好"就加规则，加规则这个方向本身是对的相反方向。

---

## 一、第一步：把抱怨拆成可诊断的症状

用户的原话通常很模糊："太啰嗦""不说人话""像机器人""不够主动""总在推卸"。先把它翻译成**输出层面的具体现象**，每条都要能用一份实际回复佐证。

拆的时候分两类：

| 症状类型 | 例子 | 提示词能否处理 |
|---|---|---|
| 取内容、排结构、停在哪 | 结论在第三段才出现、该对比的地方写成大段话、小事也铺开讲 | 能，这是主要工作面 |
| 措辞习惯、句子质量 | 用词僵硬、句子不顺、没文采 | 基本不能，见第零节 |

如果用户给不出例证，**先向用户要一两段实际输出**。没有样本就诊断，等于对着空气开药。

---

## 二、第二步：在提示词里找成因

拿到具体现象后，逐条对照下面五类成因。这五类是这一类问题最常见的来源，按出现频率排序。

### 1. 规则密度过高（最常见）

提示词里同一件事被反复规定，重要的要求被大量细则淹没。

诊断方法：统计每个模块的字数和"禁止句"数量（详见附录的统计脚本），看哪一节密度最高。经验值：**每 100—150 字出现一条限制就属于过密**，模型会把注意力分给每条细则，反而漏掉主干。

改法：这个模块整体重写，不是逐条删。留主干、删细则。

### 2. 语气规则侵入内容任务

本该只用在代码、进度汇报里的格式要求（"每条一行""像代码交接""不要说废话"），被写成了全局规则。于是用户问一个需要解释的问题时，模型也在写电报体。

改法：**给规则划适用范围**。这类规则前面加一句"只在……时适用"，其余任务不受影响。有条件的直接整块搬到独立文件，按需加载（类似把代码规范单独做成 skill）。

### 3. 规则互相矛盾，模型选了保命的那条

两条规则冲突时，模型倾向于选更保守的——每句都加免责、不敢下结论、反复确认。这不是模型笨，是提示词逼的。

诊断方法：把提示词里所有指向同一行为的要求找出来读一遍，看有没有"A 要简短"和"B 要说清理由"这种暗中冲突。

改法：合并成一条，写成**有明确优先级或明确条件**的表述，而不是并列存在。

### 4. 要求放错位置

该近的规则离问题很远。用户抱怨"回复总在最后一段才给结论"，规则却散在文末的某个附录里。

改法：把这条规则挪到对应任务说明的**紧邻位置**。位置比措辞重要。

### 5. 只有否定，没有替代

"不要用感叹号""不要写免责声明""不要用对比句式"——模型知道不该做什么，但不知道**该做什么**。结果是它绕开禁令，选了另一种同样难看的写法。

改法：每条否定后面必须有正面出口。**"不要写 X，改成写 Y"**，或者干脆只写 Y。没有出口的禁令应当删除，而不是补一句"记得别用 X"。

## 三、第三步：四类规则，四种处理

找到成因之后，逐条判断这块规则属于哪一类。**错在这里会前功尽弃**，必须分类再动手。

| 类别 | 特征 | 处理 |
|---|---|---|
| **措辞形式类** | 管句式、标点、比喻、加粗、条目、篇幅、开头结尾怎么写 | **直接删**。这是"限制越少越会写"的作用区。常见例子：不要用冒号引结论、不要用对比句式、不要发明比喻、每条一行、不要写"我将会" |
| **事实诚实类** | 管数字真不真、做没做的事说不说、承认不承认不确定 | **保留**，可改写得更直接。常见例子：说清做了什么没做什么、数字给实数、没验证就说没验证 |
| **交付格式类** | 管接口、字段、文件路径、代码块、表格、固定输出结构 | **保留**，但写成"约定+例外"的形式。常见例子：回复里的链接位置、代码块必须可运行、文档必须给路径 |
| **受众目的类** | 管"对方从这段文字里能得到什么" | **保留甚至加强**。常见例子：先给结论、外行能看懂、术语要解释、说清这对用户意味着什么 |

**最关键的一条**：删措辞禁令的时候，只删措辞，不要顺手删掉混在同一节里的内容要求和行为要求。真实事故记录：曾有一轮改写把"不要用冒号""每条一行"这类禁令连同同节的四条要求一起删了，用户的直接反馈是"最新版回复质量不如第二新"。被误删的典型是这类句子：

- `Include technical details only when they help explain or support the point`（该详细时要详细）
- `Give the user enough context to follow their reasoning`（要给够背景）
- `先说一句它是什么意思`（术语要解释）
- "我明确要求你主动提建议和顾虑"（主动性要求）

删完之后必须**逐条比对上一版**，确认这四类内容要求一条没少。有一个简单的核查办法：把两版的"规则清单"各自列出来，标出每条属于哪类，检查"事实/交付/受众"三类的条目数有没有减少。

另一条必须记住的反例：**不要写"每条不超过两句""不要切成小条目""三条以内写成一段"**。这三条看似在治啰嗦，实际会同时削掉密度和结构，而用户真正想要的往往是"逻辑密集但排得好"。篇幅问题应当通过"结构量跟着请求量走"解决，而不是靠砍句子。

## 四、第三个视角：整体性——一份提示词是一个系统

单条规则怎么改都有道理，但放在一起可能互相抵消。改之前先回答四个问题：

1. **这份提示词想让模型默认做什么、只在什么条件下偏离？** 这个"默认动作"必须能在提示词里找到一句明确的话。找不到，模型每天在猜。
2. **删掉一条规则之后，原本被它压住的行为会不会反弹？** 例：删掉"不要重复上一句"，模型可能开始复述；这时候需要在新规则里加一条正向要求"每句话带来新信息"来顶住，而不是留着原禁令。
3. **文末的规则和文首的规则谁赢？** 模型没有严格的优先级系统，但**位置靠后、语气更具体、篇幅更长的规则通常权重更高**。需要让某条规则占上风时，把它放在对应任务附近并说清"和其他要求冲突时以本条为准"。
4. **总字数降了，注意力是否真的转移了？** 验证办法不是看字数，是看改完之后"哪一句话会让模型停下来想一下"。如果是新加的中文规则让模型停顿，说明它生效了；如果还是原来那几句英文禁令，说明删得不够。

---

## 五、第四个视角：科学性——改完必须验证

提示词改动的效果极容易被主观感受欺骗。必须遵守下面三条，否则容易把错觉当效果：

### 1. 评分表要在跑之前定死

先写下"什么叫好"，再去看产出。评分维度要么直接来自用户的抱怨，要么来自上一轮的失败点。**不要在看过产出之后再补维度**——那是给已有结果找理由。

评分维度不要用"是否简短""是否有表格""是否超过 300 字"这类**形式指标**当主指标。它们和用户的真实满意度相关性很低。用**"读者能不能用得上这段文字"**一类的维度：结论是否先到、外行能否看懂、不确定处是否说清了能判断什么。

### 2. 两组对照跑同一个题目

同一批题、同一个人（或同一模型同一设置）同时跑新旧两版提示词。一次只换一个变量。

如果时间或成本不允许双跑，至少做三件事：

- 从旧版本里挑 2—3 份最典型的产出作为基线；
- 新版本跑**同一批**题目；
- 逐题对比"读者现在能多知道什么"。

### 3. 如实写出平局和盲区

平局是正常结果，不是失败。一份诚实的评测结论长这样：

> 两版在上述维度上打平。这意味着这轮改动在这批题上测不出差别。可能的解释：①这批题不涉及这一层能力；②评分维度已经饱和；③改动本身无效。下一步应换一批题，覆盖多轮纠偏场景。

**只要有平局，结论里就要写清楚"这轮测不到"和"下一步应该怎么测"**，不写"新版更好"。

已知的盲区，务必在结论里点出来：

- **单轮写作题测不到多轮场景**：用户真正满意与否往往出现在"改需求、带工具、要它自己判断该不该问"这类对话里，不是一道题一次性写完。
- **单评人不盲评会偏向新版**：知道哪份是自己改的，会下意识觉得新版好。
- **样本量小于 10 时不要下"更好/更差"的结论**，只说"未观察到差别"。

### 4. 区分"呈现变好"和"能力变好"

这是最容易被误读的一条。**两份不同提示词下，如果同一模型写出了更清楚、更有条理的内容，多半是它把同样的内容排对了，而不是它变聪明了。**

实测记录：27.5k 与 24.3k 两版提示词跑 13 道题，句子完整、外行能懂、先给答案、不确定处说法四个维度全部打平（各 26/26），真正的差别在结构化程度——加粗的结论、对照表、编号清单。这意味着改动确实有效，但**有效的方式是"编排"，不是"文笔"**。

给用户下结论时，把这两个层面分开说：

> 提示词改动之后，模型给的内容本身没有变化，变化的顺序、分块、和每一段"说这有什么用"。你觉得更好读，是因为重点被摆到了前面；句子还是原来的句子。

这样用户不会对提示词的期望错位，也不会下次遇到"句子写得难看"时以为改提示词能解决。

## 六、技巧层：具体怎么写

### 正面表述优先

| 不写 | 改写成 |
|---|---|
| 不要写"不能据此判断" | 正面说这个结论覆盖到哪里（"只能判断 A，B 要看实际课稿"）；或者直接给猜测，标"我猜""有可能" |
| 不要用术语 | 术语只在你用过、或者不用就说不清时才用；用的时候先说一句它是什么意思 |
| 不要先说背景再说结论 | 先给结论或成品，再用完整句子说明原因 |
| 不要重复上一句 | 每句话都要带来新东西 |

### 把"格式关切"翻译成"内容要求"

用户抱怨"太啰嗦"时，他真正想要的往往是：

- 不重复（→ 每句话带来新东西）
- 不预告（→ 直接说结论）
- 不堆免责（→ 说清楚能判断到什么程度）

这三条都能写成内容要求，不需要写"每条一行"。

### 关于结构的量

模型最常见的副作用是"结构过量"：一句"好"也要回一张表。修正方式不是让模型变短，而是**让结构的量跟着请求的量走**。可以写：

> 简单问题直接用一段话回答；需要对比几样东西、列清单、讲流程时才上结构化形式。

不建议写"不超过三条""不要列表"——用户明确说过喜欢表格和图示。

### 语气类的写法

用户觉得"像机器人""太生硬"这类抱怨，正确的改法通常不是加形容词，是**给一个具体的参照**：

> 像跟同事说话那样写：用熟悉的词，具体例子，日常说法。

比"请用自然、亲切的语言"有效十倍，因为后者可以被任何模型用任何方式满足。

### 中文规则可以覆盖英文规则，但要写清楚

如果原提示词是英文的，用户的要求是中文的，直接加一节中文规则放在末尾，并写一句明确覆盖的话：

> 本节优先于上文英文部分的写作要求。

不写这句，模型会在两套风格之间摇摆。

## 七、交付什么

一次完整的提示词诊断，交付四样东西；缺任何一样，用户下次还会问同样的问题：

1. **诊断**：问题现象 → 对应到提示词里的第几条 → 为什么这条会导出这个结果。每条都要能指到原文的句子。
2. **改写**：改了什么，属于四类的哪一类，为什么这样处理。删的每条都要说明"为什么删了不反弹"（见第四节第 2 点）。
3. **改不了的**：不属于提示词能处理的部分，明确说出来，给替代方案。
4. **验证结果**：怎么测的，测到了什么，哪些东西没测到。

**交付前自检**（逐条打勾）：

- [ ] 事实诚实类、交付格式类、受众目的类的规则，条目数没有比上一版少
- [ ] 没有新增任何"每条一行""不超过 N 句""不要列表"这类篇幅禁令
- [ ] 每条保留的否定都有正面出口
- [ ] 覆盖关系写清了（中文覆盖英文、skill 覆盖通用规则时）
- [ ] 评分表是在跑之前定的
- [ ] 平局或没测到的部分，写进了结论

## 附录：统计脚本

诊断提示词时，先跑统计拿到客观底数。完整可用版本在 `codex-plain-style` 仓库的 `eval/stats.py`，直接复用；没有仓库时用下面这份最小版，保存为 `.py` 文件、用数据路径作参数运行，避免把提示词内容贴进对话。

```python
# stats.py <提示词文件>
import re, sys

t = open(sys.argv[1], encoding="utf-8").read()

# 按一级/二级标题切模块
parts = re.split(r"\n(?=#{1,2} )", t)
rows = []
for p in parts:
    head = p.split("\n", 1)[0].strip()
    rows.append((head[:40], len(p), len(re.findall(r"\bdo not\b|\bdon't\b|\bnever\b|\bavoid\b|\bunless\b", p, re.I)),
                 len(re.findall(r"不要|禁止|不得|不能|避免", p))))

print(f"总计 {len(t)} 字符 / {t.count(chr(10))+1} 行 / 中文 {len(re.findall(r'[一-鿿]', t))}")
print(f"{'模块':42} {'字数':>6} {'英否':>5} {'中否':>5}")
for h, n, e, c in sorted(rows, key=lambda x: -x[1])[:20]:
    print(f"{h:42} {n:6} {e:5} {c:5}")
print("禁止句密度 = 否定句数 / 字数 × 1000，超过 8 视为过密")
```

**注意这个脚本和统计文档的计数口径不同**：脚本用 `findall` 数的是**词频**，统计文档数的是**含该词的句子数**。一句话里同时出现 `do not` 和 `unless`，脚本记 2、文档记 1。两种口径都可用，但同一份对比里必须统一；对外报告时说明用的是哪一种。

同一份提示词的两种口径实测（custom 版）：句子口径 61，词频口径 52（44 个英文否定词 + 8 个中文否定词，这 8 个分布在 6 句里）。出厂模板的对应数字是 86 和 70。差异不小，所以**报"禁令降了百分之多少"时必须说明用的是哪种口径**。

这个脚本给的是**线索，不是判决**。密度高不等于该删——还要看是什么类别（第三节）。密度低也可能出问题，比如整个提示词对某个关键行为只字未提。

## 这个 skill 的来源

这套流程来自 2026-11 对 Codex 系统提示词的一次完整改造：症状是"不说人话、太防御、不主动"；诊断后发现主因是 `## Writing Style` 一节的 2,545 字里塞了 20 条措辞禁令（每 127 字一条）；改写把这一节砍到 733 字，含禁令的句子从 86 降到 61（句子口径，词频口径 70→52，两条硬禁止一类的词 59→36），把代码规则整块外移，新增 1,581 字中文规则（全部属于受众目的、事实诚实、行为边界三类）；两轮 13 题 × 3 臂评测给出了答案：内容六维（句子完整、外行能懂、先给答案等）三臂全部打平（出厂模板 156 / 上一版 154 / 当前版 154，满分 156），说明改版没让内容变好；换一套评"主观可用性"的表（一眼看到重点 / 结构服务内容 / 读完的意愿 / 能直接抄用的句子）再测，出厂模板 128 / 上一版 134 / 当前版 140，差别出现了。结论：**改版改的是编排层，不是内容层。**

统计数字、事故记录、评测结论均可用项目内的 `系统提示词改造统计-2026-11-18.md` 和 `codex-评测评分-2026-11-18.md` 复核。
