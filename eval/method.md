# 对照评测方法

这套方法用回答一个问题：**改了提示词之后，模型的输出是不是真的变好了？** 它的核心不是跑模型，是防止用主观感受代替证据。

---

## 一、三臂设计

同一批题、同一个模型、同一个设置，只换 `model_instructions_file` 指向的提示词文件。

| 臂 | 提示词 | 作用 |
|---|---|---|
| A | 上一版改版（例：v27508，27,508 字符） | 对照，判断这次改动有没有引入退步 |
| B | 模型出厂模板（例：`gpt-6.2-sol-original.md`，27,750 字符） | 基线，判断整条改造路线有没有意义 |
| C | 当前在用版（例：24,310 字符） | 待测 |

**B 臂不可省略。** 只有 A 和 C 的时候，两版打平就意味着"这轮改动无效"和"这套题测不到"两种结论无法区分。加上出厂模板，至少能回答"改造路线本身有没有用"这个大问题。

**如果 C 相对 B 是明显改善、相对 A 打平**，正确结论是：改造在早期版本就已经把该改的问题改完了，后续版本是大扫除。这是好事，也是文章里最有力的证据——它说明问题出在哪、修好之后稳定。

---

## 二、跑法

```bash
# 1. 准备题目：一题一个 .md，题干即用户原话，不加任何提示
ls eval/questions/

# 2. 跑一臂（题目目录与产出目录都是参数）
./eval/run-arm.sh A ~/.codex/prompts/上一版.md
./eval/run-arm.sh B ~/.codex/prompts/gpt-6.2-sol-original.md
./eval/run-arm.sh C ~/.codex/prompts/当前版.md

# 3. 统计（客观底数，不进评分）
python3 eval/stats.py ~/.codex/prompts/当前版.md

# 4. 从 rollout 里取回三臂产物（以会话记录为准，不靠文件名归属版本）
python3 eval/extract.py --date 2026/11/18 --out /tmp/eval/raw

# 5. 打乱编号、生成盲评包（key 单独保存，不给评分者看）
python3 eval/blind_pack.py --raw /tmp/eval/raw --out /tmp/eval/blind --key /tmp/eval/key.json

# 6. 收齐评分后汇总
python3 eval/tally.py --key /tmp/eval/key.json --scores /tmp/eval/scores
```

注意事项：

- `codex exec` 必须用 stdin 重定向（`< q.md`）。把题干作为位置参数传入会让它停在 "Reading additional input from stdin..."。
- `-o` 指定的输出文件只在进程退出时写入。文件是 0 字节说明还在跑。
- 每题单独一个进程，避免多轮上下文互相影响。要测多轮，另设一组题目，不要把两轮塞进一个 `exec`。
- 每题单独计时。出厂模板的提示词要求先核实，很多题会联网搜索，单题可能跑几分钟。
- 题目语言和提示词语言要一致，否则会掺入语言混杂的干扰（中文题面 + 纯英文提示词，模型可能整段用英文答，这和提示词质量无关）。

## 三、评分

### 3.1 两张评分表，回答两个不同的问题

| 评分表 | 问的问题 | 维度 | 什么时候用 |
|---|---|---|---|
| `eval/rubric.md`（v1，六维） | 内容能不能用上 | 句子完整、外行能懂、先给答案、不确定处的说法、有具体东西、有判断和提醒，各 0—2 | 判断改版有没有把内容改坏 |
| `eval/rubric-v2.md`（v2，四维） | 读者会不会觉得更好用 | 一眼看到重点、结构服务内容、读完的意愿、能直接抄用的句子，各 0—3 | 判断改版的编排有没有价值 |

两张表单题都是满分 12、13 题满分 156，但分数**不可互相比较**，只能比"哪张表分得开这三臂"。实测：v1 三臂 156/154/154 饱和；v2 三臂 140/134/128 分开了。两张表一起跑，结论才完整——v1 说内容没变，v2 说摆法变了。

### 3.2 盲评的做法

1. 用 `extract.py` 从 `~/.codex/sessions/` 的 rollout 里按 `base_instructions` 长度取回各臂产物。**不要用 `run-arm.sh` 输出的文件名当版本依据**——文件名是人起的，rollout 里的提示词是实际生效的。
2. 用 `blind_pack.py` 按固定种子（`20261119`）把每题三份随机编成 X/Y/Z，key 写到单独文件。
3. 评分者只拿到题目和自己的三份答案，不知道版本，**不跨题横向比较**。
4. 每位评分者负责一段题号，互不通气；每条分数必须引一句回答里的具体位置，不接受"结构好""表达清楚"这类笼统理由。
5. 两人以上独立评。分歧 ≥3 分的题进入复核；本轮 13 题没有出现需要复核的分歧。

### 3.3 评分时的三条纪律

1. **先看产出，再看是哪一臂**。盲评包里没有版本信息，这条自动满足。
2. **篇幅、表格数量、加粗数量不直接给分**。v2 评的是"读者有没有因此更快拿到重点"，排得再多但重点仍埋在中间，就该低分。
3. **打平就写打平**。平局是正常结果，不是失败。平局时必须写清"这轮测不到什么"和"下一步应该换什么题"。

## 四、如何解释结果

结果组合只有四种，对应的结论各不相同：

| B vs C | A vs C | 结论 |
|---|---|---|
| C 明显更好 | C 更好 | 每一步都有效，保留最新版 |
| C 明显更好 | 打平 | 改造路线有效，早期版本已完成主要修复；后续是清理，不是能力提升 |
| C 略好 / 打平 | C 更差 | 提示词改动引入了退步，回退到 A，重新定位删多了什么 |
| 全部打平 | — | 要么这批题测不到，要么改动无效。先换题，再下结论 |

**"C 更好"必须细分成两层**：内容层（说了什么）和编排层（先说哪个、怎么分块、哪里加粗）。提示词最容易改的是编排层。如果只有编排层改善，给用户的结论要写成：

> 模型给出的内容没有变，变的是顺序和分块。你觉得更好读，是因为重点被摆到了前面。

不要说成"模型变得更会写了"。这一区分决定了用户下一次遇到"句子写得难看"时，会不会误以为改提示词能解决。

## 五、实际跑过两轮，每一步长什么样

### 第一轮：v1 六维表

1. 三臂各跑 13 题。B 臂第一次跑废了：用户记忆里的写作要求被注入进了上下文。"第一次跑 B 时，注入的 `AGENTS.md` 带着刚定下的写作要求"——等于给对照组开卷。
2. 重跑 B，把两次注入块逐字节比对，确认差别只有工作目录一行、不含 `~/.codex/memories/` 下任何文件。这一步必须做，不能凭"应该没进"。
3. 单评人按 v1 打分：B 156 / A 154 / C 154，满分 156。13 份 B 产物全部满分。
4. 结论：这张表饱和。不能写"三个版本一样好"，只能写"这批题问不出三臂的区别"。

### 第二轮：v2 四维表

1. 用 `extract.py` 从第一轮的 rollout 里取回三臂产物，各 13/13。
2. `blind_pack.py` 生成 13 个盲评包，key 与 /tmp 下的 raw 分离。
3. 三位独立评分员分三段题号打分，共 39 条评分记录（13 题 × 3 臂），每条四个维度分数。
4. `tally.py` 汇总：C 140 / A 134 / B 128；"本题最好"票数 C 7 / A 3 / B 3；"读完的意愿"维度差距最大（31/29/26）。
5. q05、q06 三份同分——同一交付物的不同写法，差剧本就不存在。这种情况如实写"打平"，不为凑差别硬选。

### 两轮拼起来怎么说

> 内容三家一样，摆法 C > A > B。第一轮因为不评摆法所以打平，第二轮因为评摆法所以拉开。改版改的是编排层，不是内容层。

单看任何一轮都会得出片面结论：只看 v1 说"改版无效"，只看 v2 说"改版更好"。两轮都要报。

## 六、已知限制（引用结果时必须一起给出）

- 单轮题不覆盖多轮、带工具、中途改需求的场景。
- 评分表容易饱和；多数题满分时无法区分两版。
- 单评人、不盲评时存在偏向新版的系统性偏差。
- 同一次评测里如果 effort / 温度 / 是否联网不一致，结果不可比。桌面端和 CLI 的默认设置也可能不同。
- 样本量小于 10 时，只写"未观察到差别"，不写"更好"或"更差"。
- 题干改写后旧的 rollout 匹配不上。`wb901-scope.md` 在 2026-11-19 去掉了具体课文名，rollout 里记的是改前的问法，所以按今天的题面重跑 `extract.py` 会报 12/13，`wb901` 那一题落在 missing 里。`results.md` 里的分数来自改写前那次完整抽取；重跑时不要把它当数据丢失。
- v2 这类主观表会奖励"排版漂亮的空话"。靠"能直接抄用的句子"一维压着——要求有一段能原样贴进工作，而不是"N 处具体内容"。
- 评分员人数（本轮三人）不代表真实用户分布。分歧小只能说明"这批题上评分员看法一致"，不能说明"所有人都会这么选"。
